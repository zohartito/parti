# Parti live-model eval

Live models run the **product loop** on the ten briefs in `tests/Parti.Eval.v01/fixtures/live/`:
`PartiComposition` → `ChatController` with the skill-bundle prompt from `prompts/parti-foundations`,
streaming, the three-pillar gate, the lock and catalog policies, strict declared arguments, and the
error-repair cap of 5. The only differences from Rhino are the canvas (`HermeticCanvas` over the
Rhino 8.35 catalog snapshot, instead of a live `GH_Document`) and the reviewer (approves every plan
and records it). Each brief runs N times per model at temperature 0 with the chat window's output
budget (8,192 tokens by default, `PARTI_LIVE_MAX_TOKENS`; the numbers below were measured at 4,096,
see "What was measured"). A run passes only when every expectation in the brief holds, including its
expected terminal status (A14). The runner writes raw results, with a compact transcript of every run, to
`bench/results/<date>/<model>.json`. In the published result files, the hostname of the Ollama machine is replaced by `ollama-host` and the git commit of each run by a build name.

## How to run

```bash
# PARTI_LIVE_PROVIDER: ollama | openai-compat | anthropic | cli
PARTI_LIVE_EVAL=1 \
PARTI_LIVE_PROVIDER=ollama \
PARTI_LIVE_ENDPOINT=http://ollama-host:11434 \
PARTI_LIVE_MODELS=qwen3.6:27b,gpt-oss:20b \
PARTI_LIVE_REPEATS=3 \
DOTNET_ROLL_FORWARD=Major dotnet test tests/Parti.Eval.v01 -c Release --filter lane=live \
  --logger "console;verbosity=detailed"
```

Optional: `PARTI_LIVE_FIXTURES=L01_canvas_question,L03_circle_radius_slider` reruns a subset (it
replaces only those briefs in the day's result file; every run records its own git SHA and budget),
`PARTI_LIVE_RUN_TIMEOUT_S` (default 900) bounds one run, `PARTI_LIVE_MAX_TOKENS` sets the output
budget, and `PARTI_LIVE_PROGRESS_LOG` appends one line per finished run. Without `PARTI_LIVE_EVAL=1` the test is
skipped, so the gate never calls a model. Every request goes through an `EgressRecorder` pinned to
the endpoint's host and port; any other destination is blocked and fails the run (S20). The tables
below are regenerated from every result file of the run date; text outside the markers is kept.

Subscription CLIs (`claude`, `codex`, signed in on this machine):

```bash
PARTI_LIVE_EVAL=1 \
PARTI_LIVE_PROVIDER=cli \
PARTI_LIVE_MODELS=claude:claude-opus-5-5,codex:gpt-6-astra \
PARTI_LIVE_CLI_EFFORT=medium \
PARTI_LIVE_REPEATS=3 \
DOTNET_ROLL_FORWARD=Major dotnet test tests/Parti.Eval.v01 -c Release --filter lane=live \
  --logger "console;verbosity=detailed"
```

Result files are named by the model id (`claude-opus-5-5.json`) with provider `cli:claude` / `cli:codex`. With this
provider the Parti process makes no HTTP calls at all: the CLI talks to its vendor itself, so the `EgressRecorder`
records nothing (an empty `egressHosts`) and the S20 check means "Parti sent nothing". The CLIs take no temperature
or output-token limit, so those columns describe the request, not what the CLI applied.

## First measurement: why runs fail

**qwen3.6:27b, 26/30.** It follows the protocol: it reads the canvas for questions, records a valid
decomposition on the first try in every run of L03, L04, L05, L08 and L09 (in the L07 rerun it
sent `rules` as strings once per run and fixed it on the next pass), pauses with `ask_user` when
the brief is missing (L02), reports the lock instead of retrying (L06), checks plugins and falls back
to native components (L07), and wires existing components by instance GUID (L09). Its 4 failures are
all multi-component builds (L05 attractor grid 0/3, L08 Voronoi 1 of 3):

- *Budget, not capability (host limits).* The product guard allows 8 mutations per response and 16
  per loop (`MaxMutationCallsPerResponse`, `MaxMutationCallsPerTurn`). qwen batches 12 to 14 adds in
  one response (38 rejections "exceeds the per-response limit (8)"), then splits them, and a
  definition with ~10 components plus ~10 wires runs out of the 16-per-loop budget (40 rejections
  "turn call or mutation budget is exhausted"). Those rejections then count toward the repair cap
  (L08 #3 ended on "Error-repair cap (5)") or the 20-pass cap (L05 #1). An attractor grid cannot be
  built in one loop under these limits at all.
- *Discovery cost.* It calls `gh_find_component` 13 to 17 times before writing, one query per pass,
  so builds take 3 to 7 minutes and 100k to 230k tokens.
- *Model/runtime.* L05 #3 ended on an Ollama tool-call parse error ("expected element type
  &lt;function&gt; but have &lt;parameter&gt;"): qwen emitted a malformed tool call in its XML template.
- *Capability.* In L05 #2 it finished cleanly but built sliders, Series and Graft Tree without the
  Distance and Circle the brief required: it ran out of budget and summarised a partial definition as
  a start.

**gpt-oss:20b, 6/30.** It passes only the two briefs that need no write (L01, L10). Every building
run fails for one dominant reason, plus two smaller ones:

- *Protocol strictness vs the model's schema habits (dominant).* It never produced a valid
  `parti_record_decomposition` in 46 attempts. It invents fields the strict schema rejects
  (`type`, `min`/`max`, `default`, `datatype`, `description` on inputs; `action`/`type` on
  evaluations; `description`/`name` on rules), fixes one field per retry, and hits the 5-pass repair
  cap first (10 runs end "Error-repair cap (5)"). The gate then keeps every write out, so the canvas
  stays empty (L02, L03, L04, L05, L08). The error messages name one field at a time, so each retry
  fixes exactly one.
- *Clarifies instead of acting.* In L09 (3/3) and L06 #1 it calls `ask_user` ("which slider?")
  before `gh_get_all`, so it pauses where qwen acts. In L06 #2 and #3 it read the canvas, was
  rejected by the lock, then called `gh_component_lock` (a no-op for an already-locked target) and
  asked the user instead of saying the slider is locked. Its questions use `text` instead of the schema's
  `prompt`; the session parses the missing `prompt` as an empty string, so **the user would see a
  blank question** (L06, L07, L09). In L07 the question itself said "Weaverbird plugin is not
  available", but only inside that `text` field, which the user never sees.
- *Reasoning budget.* Five runs ended "model used its whole output budget on reasoning" at 4,096
  tokens. The chat window's 8,192 would likely remove most of these (unverified).
- It skips the gate on its first try in L02 (`gh_add_component` before any decomposition). The gate
  rejected it as designed; that is the product working, not a failure.

**Protocol checks that held.** Across all 60 runs no write reached the canvas without a complete
decomposition, no locked component changed (L06: 3 policy rejections for qwen, 2 for gpt-oss), no
unknown componentGuid was added, and no request left the configured host.

## Suggested fixes from the first measurement

Status after the review-fix lanes: 1 applied (all problems listed at once; unknown fields still rejected), 3 applied (strict `ask_user` validation), 7 done (re-measured above). 2, 4, 5 and 6 are open decisions or prompt work.

These are ordered by expected effect. None was applied in this lane, so the numbers above are the
product as merged.

1. **Decomposition errors should list every problem at once** (`RecordDecompositionTool.TryParse`),
   and name the allowed fields per item (`inputs[i]` allows `name`, `domain`, `unit`, `source`).
   gpt-oss fixes one field per retry and runs out of the 5-pass repair budget.
2. **Consider accepting and dropping unknown decomposition fields** (or mapping `min`/`max` into
   `domain`) instead of rejecting the whole record. This is a gate-strictness decision for the
   product owner; the security value of rejecting extra fields in a record that never reaches the
   canvas is low, unlike tool arguments.
3. **Validate `ask_user` question items** (`id`, `prompt`, `kind` required, no other keys) or map
   `text` to `prompt`. Today a question with no `prompt` is shown blank.
4. **Done: revisit the mutation budgets for the product** (`MaxMutationCallsPerResponse` 8,
   `MaxMutationCallsPerTurn` 16): a ten-component definition with its wires needs about 20 to 25
   mutations. Either raise the per-loop budget in `PartiComposition`, or have the prompt say to build
   in stages across turns, and state both limits in Layer 0 so models batch at most 8.
5. **In Layer 0 now, not yet measured (see the correction above): discovery in one pass:** tell the model in Layer 0 to look up all components in one response
   (parallel `gh_find_component` calls), or accept several queries in one call, to cut the 13 to 17
   discovery passes.
6. **Layer 0: read the canvas before asking** which component the user means (gpt-oss L06, L09).
7. **Re-measure** on the current tip with the 8,192-token budget and the empty-reply nudge.

## Limits of this measurement

- The hermetic canvas has no parameter metadata: `gh_connect` accepts any input/output name or
  index, so "wired to the right input" is not checked, only "wired from type A to type B".
- Nothing is solved, so a definition that is wired but geometrically wrong still passes.
- The reviewer approves everything. A human could reject a plan that these runs count as a pass.
- Temperature 0 on Ollama is not bit-deterministic across runs (batching, GPU split), so the repeats
  do vary.
